# Пространства идентичности PUB

Этот документ фиксирует только те различия и связи между идентификаторами, которые уже имеют подтверждённый статус в каноническом реестре проекта.

Главное правило: совпадение чисел не означает совпадение пространства идентичности.

## Подтверждённые пространства

### Contents 0x22: objectId / parentId

Для проверенных Publisher 98/2000 каталог Contents является компактным списком живых записей. Каждая запись явно хранит:

- `u16 objectId`;
- `u16 parentId`.

Пропущенные objectId не занимают отдельные позиции каталога.

Это пространство нельзя автоматически переносить на 0x2C.

Основание: Canonical Claim #98, OBS-OPL-EPOCH-01.

### Contents 0x2C: seqNum как номер позиции

В проверенных нативных Publisher 2002/2003 каталог Contents устроен как разреженная таблица позиций:

- номер позиции каталога является `seqNum`;
- отсутствующие позиции сохраняются как явные DUMMY-слоты `00 78`;
- занятая запись не хранит отдельный seqNum внутри самой записи каталога.

Поэтому в фундаменте пока не вводится искусственная «ширина поля seqNum»: доказанный факт состоит в том, что это номер позиции каталога.

Основание: Canonical Claims #94 и #98, OBS-OPL-EPOCH-01.

### Quill SYID

В проверенной грамматике Quill SYID:

- служебные значения заголовка хранятся как `u32`;
- количество идентификаторов хранится как `u32`;
- каждый элемент массива SYID хранится как `u32`.

Для Publisher 98/2000 массив story ID в Contents TextZone 0x52 точно совпадает с Quill SYID в проверенных файлах.

В позднем 0x2C story-каталог 0x65 также сопоставляется с Quill SYID, но конкретные носители связи должны сохранять собственное происхождение.

Основание: Canonical Claims #5, #8 и #32; OBS-010B.

### Oid

Для позднего 0x2C Publisher `Oid` имеет подтверждённое исходное представление ровно из 8 байт.

Подтверждено также:

- Oid является отдельным пространством идентичности;
- Oid не равен физическому `oh/seqNum`;
- один и тот же Oid может повторяться у разных физических объектов в разных сценарных экземплярах;
- нулевой Oid допустим.

Основание: Canonical Claim #17; OBS-034.

### Pgid

В проверенном позднем 0x2C `OplPageListInfo.Pgid` точно совпадает со значением `Page.Oid`.

Это подтверждает связь значений, но не даёт права считать Pgid физическим `seqNum`.

Основание: Canonical Claim #80; OBS-035.

### Quill descriptor id для TOKN/TCD

Для проверенных story-scoped TOKN/TCD поле descriptor id — это нумерация истории с нуля внутри параллельных массивов SYID/STRS.

То есть:

`descriptor id -> индекс истории -> SYID[index] -> persistent story ID`.

Descriptor id нельзя напрямую считать storyId/textId.

Основание: Canonical Claim #53; OBS-015B.

## Что пока намеренно НЕ кодируем как единую систему

Пока не должно существовать:

- универсального `native_id`;
- автоматического преобразования `0x22 objectId <-> 0x2C seqNum`;
- автоматического преобразования `seqNum <-> Oid`;
- предположения, что одинаковые числовые значения из Contents, Quill и Escher означают один объект;
- единого «ID страницы», объединяющего PAGE seqNum, Page.Oid, Pgid и другие пространства;
- связи с `spid`/`lTxid` без отдельного подтверждённого правила и происхождения.

## Типы, которые уже допустимы в фундаменте

На текущем уровне доказательств безопасно ввести только физически закрытые типы:

- `Contents0x22ObjectId(u16)`;
- `QuillSyid(u32)`;
- `PublisherOid([u8; 8])`.

Для `0x2C seqNum` отдельный числовой wire-type пока не вводится: доказан номер позиции каталога, а не самостоятельное поле с универсальной шириной.

Любая будущая связь между этими типами должна быть отдельным ребром `IdentityGraph` с происхождением доказательства.
