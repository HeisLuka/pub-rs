# Архитектура

`pub-rs` отделяет истину о хранении данных от удобных моделей для отображения и редактирования.

## Допуск фактов в фундамент

Фундаментальный код может закреплять только факты с явно указанными доказательствами и областью действия.

- Сырой факт остаётся сырым, пока его семантика не доказана.
- Разные идентификаторы остаются разными, пока связь между ними не доказана.
- Факт, подтверждённый для одного бинарного семейства, не становится автоматически универсальным.
- Гипотезы живут в исследовательских заметках, экспериментах или явно помеченных декодерах, но не в канонических фундаментальных типах.
- Новые открытия должны расширять модель, а не заставлять переосмысливать уже сохранённые исходные байты.

## Слои

1. **RawPublication** — неизменяемые исходные байты потоков и дерево записей; неизвестные данные сохраняются.
2. **IdentityGraph** — собственные идентификаторы формата и только доказанные связи между проекциями.
3. **SemanticPublication** — страницы, фигуры, истории текста, стили и ресурсы, поднятые из сырых проекций.
4. **ResolvedPublication** — эффективные значения после применения значений по умолчанию и наследования.
5. **Запись проекций** — Contents, Quill, Escher и другие собственные представления PUB.
6. **Адаптеры отображения и экспорта** — только потребители; никогда не каноническое хранилище.

## Правило идентичности

У Publisher нет доказанного универсального типа `native_id`.

Идентификаторы последовательности/объектов Contents, идентификаторы историй/текста Quill, идентификаторы фигур/текста OfficeArt и другие собственные пространства остаются раздельными, пока конкретное соответствие не доказано. Физические смещения — это происхождение данных, а не семантическая идентичность.

Подтверждённая карта пространств и запрещённых автоматических преобразований ведётся в [IDENTITY.md](IDENTITY.md).

## Правило исходных байтов

`RawSpan` — это адрес участка внутри неизменяемого `RawPublication`. Поэтому неизвестные и повреждённые элементы могут оставаться восстанавливаемыми без потерь, не заставляя каждый узел парсера дублировать свой набор байтов.

Пути контейнера представлены типом `StreamPath`; они не называются `StreamId`, потому что MS-CFB уже определяет stream ID как числовой идентификатор записи каталога.

## Первый этап

Инспектор семейства 0x2C без потери данных: перечислять потоки CFB, сохранять происхождение, постепенно декодировать Contents/Quill/Escher, выдавать детерминированный JSON и не терять неизвестные данные.

## Направление записи

`существующий PUB -> семантическое изменение -> граф изменений -> выборочная пересборка проекций -> корректный PUB`.
